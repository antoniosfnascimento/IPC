# Use Cases (CityFlow MVP)

This section details the main interactions, turning Functional Requirements into logical sequences between the system and the actors (users with or without limitations).

| ID | Use case | Primary actor | Main flow (step by step) | Expected outcome |
| :---: | :--- | :--- | :--- | :--- |
| **UC01** | **Compute inclusive route** | User (João — wheelchair) | 1. Opens CityFlow.<br>2. Enters "Origin" and "Destination".<br>3. System detects the active profile (Wheelchair) and applies the mathematical weights.<br>4. Engine recomputes the lowest cost through the slope filter (< 8%) and avoids stairs.<br>5. The system draws the polyline and informs the final distance. | The user sees a route on the map with no stairs and no steep streets, ready to follow. |
| **UC02** | **Save and edit profile** | Any user | 1. Clicks the profile button on the main screen.<br>2. Tweaks the parameters (e.g. "min width: 1 m", "mode: senior").<br>3. Clicks *Save*.<br>4. Frontend stores the new state and the app applies the new rules to the next search. | Profile is active and visible as a green sticker on the corner of the map ("Senior profile active"). |
| **UC03** | **Toggle high-contrast mode** | User (Ricardo — colour-blind) | 1. Clicks the universal contrast icon (half-moon).<br>2. Frontend updates the global CSS tags (`dark_matter`).<br>3. The basemap switches from daylight colours to grey and the route line switches from blue to bright yellow.<br>4. Text gains bold font and 7:1 contrast (AA/AAA). | A perfectly visible interface for colour-blind users with very low visual load. |
| **UC04** | **Report a real-time obstacle** | User in motion (Maria — low vision) | 1. Enters Easy-Read mode.<br>2. Comes across a sidewalk torn open for utility works (no warning on Google Maps).<br>3. Long-presses (1 s) the massive "Report blocked path" button.<br>4. Frontend uses the current GPS and tells the API to mark that area as `is_blocked = True`.<br>5. System clears the current route and recomputes in the opposite direction. | The GPS re-routes and pulls Maria away from the dangerous road onto the opposite pavement. |
| **UC05** | **Read navigation instructions** | System (Web Speech API) | 1. User is mid-route following the linestrings.<br>2. Phone reaches the last 15 m before a 90° right turn.<br>3. Frontend detects the spatial trigger and fires TTS.<br>4. A natural voice says: "Attention, turn right at the square corner." | The user does not have to stare at the phone; this prevents balance loss during mechanical walking. |
| **UC06** | **Impossible-path handling** | User and routing engine | 1. User requests a route to an old monastery accessible only by long stairs.<br>2. Backend with the wheelchair profile evaluates the nodes, multiplying by 10000.<br>3. The 1.5 km graph closes (destination node isolated).<br>4. Instead of crashing, the API replies with status 424. | Frontend says with care: "Sorry, with the current limits there is no minimally safe route to that destination. Please reposition." |
