🗺️ Especificação Técnica e Arquitetura: CityFlow Inclusivo
Versão: 1.1 (Full Specification)
Documento de Referência: Bíblia do Projeto (MVP)
Paradigma: Navegação Urbana Centrada na Acessibilidade (Micro-Routing)
1. INTRODUÇÃO E LOGLINE
O CityFlow Inclusivo é uma plataforma de navegação urbana que rompe com o modelo de "Caminho Mais Curto" (Distância) em favor do "Caminho Mais Viável" (Acessibilidade). O sistema mapeia barreiras arquitetónicas invisíveis para algoritmos comuns, transformando limitações físicas em parâmetros de custo matemático.
2. ANÁLISE DE DECISÕES TECNOLÓGICAS (Justificação de Stack)
2.1. Porquê Python (FastAPI) e não ASP.NET MVC?
Embora o grupo tenha proficiência em C#, a escolha recaiu sobre Python por:
Ecossistema Geoespacial: Bibliotecas como OSMnx e GeoPandas são wrappers de bibliotecas C++ de alta performance (GDAL, PROJ, GEOS) com décadas de maturidade. Em .NET, a integração com estas ferramentas exigiria camadas complexas de interop ou bibliotecas menos maduras (ex: NetTopologySuite).
Abstração de Grafos: O NetworkX permite manipulação de grafos em tempo real com uma sintaxe muito próxima da linguagem natural, facilitando a implementação de heurísticas de penalização customizadas.
Performance no MVP: O FastAPI (baseado em Starlette e Pydantic) oferece uma performance de I/O superior, sendo ideal para um serviço que processa grandes volumes de dados geográficos em RAM.
2.2. Fonte de Dados: OpenStreetMap (OSM) vs Google Maps API
Decisão: OpenStreetMap (OSM).
Justificação: O Google Maps fornece o caminho, mas não o Grafo Raw. No CityFlow, precisamos de manipular cada aresta (rua) individualmente para injetar pesos. O OSM permite descarregar a estrutura óssea da cidade (tags de superfície, largura, escadas), algo que o Google mantém sob propriedade intelectual fechada e custo elevado por request.
3. REQUISITOS DO SISTEMA
3.1. Requisitos Funcionais (RF)
RF-01 (Gestão de Perfis): O sistema deve suportar múltiplos perfis (Cadeira de Rodas, Ciclista, Idoso) com variáveis ajustáveis.
RF-02 (Motor de Pesos): O sistema deve aplicar penalizações dinâmicas baseadas nas tags: highway=steps, incline, surface e width.
RF-03 (Roteamento): Deve calcular a rota ótima baseada no custom_weight e não apenas na distância física.
RF-04 (Persistência): O sistema deve manter uma cache local dos mapas para garantir rapidez em arranques subsequentes.
3.2. Requisitos Não Funcionais (RNF)
RNF-01 (Portabilidade): O projeto deve ser executável em Windows e macOS com um único comando (Single Source of Truth).
RNF-02 (Robustez de Dados): O sistema deve tratar dados "sujos" (ex: strings em vez de floats nas tags de largura do OSM).
RNF-03 (Tempo de Resposta): O cálculo de rota num raio de 1.5km não deve exceder 2 segundos após o carregamento do mapa.

4.2. Fluxo de Dados e Persistência
Ingestão: O OSMnx comunica com a API Overpass via HTTP.
Serialização: O grafo é guardado em formato GraphML na pasta /data/osm_cache.
Processamento: Durante a execução, o grafo é elevado para a memória RAM (objeto NetworkX.MultiDiGraph).

5.2. Limpeza de Dados (Robust Parsing)
O sistema implementa uma camada de Regex Parsing para converter dados humanos do OSM (ex: "1.5m", "narrow", "5%") em valores flutuantes computáveis, evitando erros de tipo (TypeError) em tempo de execução.
6. IMPLEMENTAÇÃO E DEPLOYMENT (Manual do Desenvolvedor)
6.1. Orquestração de Ambiente (run_backend.py)
Para garantir que um estagiário ou docente consiga correr o projeto sem configurar o Python manualmente, o script de arranque executa:
Self-Correction: Deteta o SO e localiza os binários corretos.
Bootstrap: Cria o venv e instala o pip mais recente.
Dependency Locking: Instala as versões do requirements.txt.
Auto-Reload: Inicia o uvicorn com --reload para permitir desenvolvimento "live code".

7. ESTRATÉGIA DE TESTES (Quality Assurance)
Para garantir que o backend é sólido, o sistema deve passar por três níveis de validação no Dashboard de Developer (/docs):
Teste de Limite (Boundary): Introduzir coordenadas fora do raio de Vila Real. O sistema deve devolver Erro 400 amigável em vez de crashar.
Teste de Perfil Extremo: Definir max_incline: 0.1. O motor deve encontrar a rota mais plana da cidade, mesmo que seja 500% mais longa.
Teste de Dados Sujos: Simular pedidos com strings inválidas nos campos numéricos. O Pydantic deve barrar o pedido antes de chegar ao motor.
8. CONCLUSÃO
A arquitetura do CityFlow Inclusivo foi desenhada para ser extensível. No futuro, a adição de novos sensores (ex: qualidade do ar, ruído, iluminação) exige apenas a adição de novas regras de penalização no router.py, mantendo a integridade de todo o sistema de navegação anterior.
