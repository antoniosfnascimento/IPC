CityFlow Inclusive — Technical Specification and Architecture
Version: 1.3 (multi-city routing: Vila Real + Paris)
Reference: Project bible (MVP)
Paradigm: Accessibility-centred urban navigation (micro-routing)

1. INTRODUCTION AND LOGLINE
CityFlow Inclusive is an urban navigation platform that breaks with the "shortest path" model in favour of the "most viable path". The system maps architectural barriers that are invisible to common algorithms, turning physical limitations into mathematical cost parameters.

2. TECHNOLOGY DECISIONS (Stack justification)
2.1. Why Python (FastAPI) instead of ASP.NET MVC?
Although the team is fluent in C#, the choice fell on Python because of:
- Geospatial ecosystem: OSMnx and GeoPandas wrap mature C++ libraries (GDAL, PROJ, GEOS). On .NET the integration with these tools needs heavy interop layers or less mature libraries.
- Graph abstraction: NetworkX allows real-time graph manipulation with a near-natural syntax, simplifying custom penalty heuristics.
- MVP performance: FastAPI (Starlette + Pydantic) offers great I/O performance, ideal for a service that processes large volumes of geographic data in RAM.

2.2. Data source: OpenStreetMap (OSM) vs Google Maps API
Decision: OpenStreetMap (OSM).
Justification: Google Maps gives the path but not the raw graph. CityFlow needs to manipulate every edge to inject weights. OSM lets us download the bare skeleton of the city (surface, width, stairs tags), something Google keeps closed and expensive per request.

3. SYSTEM REQUIREMENTS
3.1. Functional requirements (FR)
- FR-01 (Profile management): supports multiple profiles (Wheelchair, Cyclist, Senior) with adjustable variables.
- FR-02 (Weighting engine): applies dynamic penalties based on `highway=steps`, `incline`, `surface` and `width`.
- FR-03 (Routing): computes the optimal route based on `custom_weight`, not raw distance.
- FR-04 (Persistence): keeps a local map cache for fast subsequent startups.

3.2. Non-functional requirements (NFR)
- NFR-01 (Portability): the project must run on Windows and macOS with a single command (single source of truth).
- NFR-02 (Data robustness): the system must handle dirty data (e.g. strings in OSM numeric tags).
- NFR-03 (Response time): a route within a 1.5 km radius must not exceed 2 seconds after the map is loaded.
- NFR-04 (Realistic slope): when OSM `incline` tags are sparse, the system must derive a per-edge slope from an external elevation source.

4.2. Data flow and persistence
- Ingestion: OSMnx talks to the Overpass API over HTTP.
- Serialisation: each city graph is stored as GraphML in `/data/osm_cache`.
- Elevation enrichment: on startup the engine queries OpenTopoData (EU-DEM 25 m) for every node of every supported city and stores per-edge grades.
- Processing: at runtime each city graph is loaded into RAM as a NetworkX MultiDiGraph. The active city is selected per-request via the `city` field of the API contracts.

5. ROUTING ENGINE (Core logic)
The CityFlow differentiator is the dynamic weighting algorithm.

5.1. Penalty function (heuristic)
For every edge (e), the cost (W) is:
    W(e) = Length(e) × Penalty_total

Where Penalty_total is the product of the constraints:
- Binary filter (stairs): if avoid_stairs AND highway == steps → Penalty = 10000
- Surface filter: if surface NOT IN surface_preference → Penalty × 3.5
- Slope filter: if ABS(grade) > max_incline → Penalty × 15
- Slope soft filter: if ABS(grade) > max_incline × 0.75 → Penalty × 3
- Width filter: if width < min_width → Penalty × 5

5.2. Data cleansing (robust parsing)
The system applies a regex parsing layer to convert OSM human strings ("1.5m", "narrow", "5%") into computable floats, avoiding runtime TypeErrors.

5.3. Real elevation enrichment
On startup the engine queries OpenTopoData (free, no API key, EU-DEM 25 m dataset) for every node, derives `grade_abs` per edge, caps it at 25% and smooths short edges so that DEM noise does not produce false steep slopes.

6. IMPLEMENTATION AND DEPLOYMENT
6.1. Environment orchestration (start.sh / start.ps1)
To guarantee that an intern or faculty member can run the project without configuring Python manually, the startup script:
- Detects the OS and locates the right binaries.
- Bootstraps the venv and upgrades pip.
- Installs the requirements.
- Starts uvicorn with `--reload` and the Vite dev server.

7. TEST STRATEGY (Quality assurance)
The backend must pass three levels of validation in the developer dashboard (/docs):
- Boundary test: pass coordinates outside the radius. The system must return a friendly 400 instead of crashing.
- Extreme profile test: set max_incline: 0.02. The engine must find the flattest route in the city, even if 500% longer.
- Dirty data test: send requests with invalid strings on numeric fields. Pydantic blocks the request before it reaches the engine.

8. CONCLUSION
The architecture was designed to be extensible. Adding new sensors (air quality, noise, lighting) in the future only requires new penalty rules in router.py, keeping the entire upstream navigation flow intact.
