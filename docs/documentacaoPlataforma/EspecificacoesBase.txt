CityFlow Inclusivo — Especificação Técnica e Arquitetura
Versão: 1.3 (routing multi-cidade: Vila Real + Paris)
Referência: Bíblia do projeto (MVP)
Paradigma: Navegação urbana centrada na acessibilidade (micro-routing)

1. INTRODUÇÃO E LOGLINE
O CityFlow Inclusivo é uma plataforma de navegação urbana que rompe com o modelo de "caminho mais curto" em favor do "caminho mais viável". O sistema mapeia barreiras arquitetónicas invisíveis para algoritmos comuns, transformando limitações físicas em parâmetros de custo matemático.

2. DECISÕES TECNOLÓGICAS (Justificação da stack)
2.1. Porquê Python (FastAPI) em vez de ASP.NET MVC?
Apesar do grupo dominar C#, a escolha recaiu sobre Python por:
- Ecossistema geoespacial: OSMnx e GeoPandas envolvem bibliotecas C++ maduras (GDAL, PROJ, GEOS). Em .NET, a integração com estas ferramentas exigiria interop pesado ou bibliotecas menos maduras.
- Abstração de grafos: o NetworkX permite manipulação de grafos em tempo real com uma sintaxe quase natural, simplificando heurísticas de penalização custom.
- Performance no MVP: o FastAPI (Starlette + Pydantic) oferece grande desempenho I/O, ideal para um serviço que processa muitos dados geográficos em RAM.

2.2. Fonte de dados: OpenStreetMap (OSM) vs Google Maps API
Decisão: OpenStreetMap (OSM).
Justificação: o Google Maps fornece o caminho mas não o grafo bruto. O CityFlow precisa de manipular cada aresta para injetar pesos. O OSM permite descarregar o esqueleto da cidade (tags de superfície, largura, escadas), algo que o Google mantém fechado e caro por pedido.

3. REQUISITOS DO SISTEMA
3.1. Requisitos funcionais (RF)
- RF-01 (Gestão de perfis): suporta múltiplos perfis (cadeira de rodas, ciclista, sénior) com variáveis ajustáveis.
- RF-02 (Motor de pesos): aplica penalizações dinâmicas baseadas em `highway=steps`, `incline`, `surface` e `width`.
- RF-03 (Routing): calcula a rota ótima com base no `custom_weight`, não na distância pura.
- RF-04 (Persistência): mantém uma cache local dos mapas para arranques rápidos.

3.2. Requisitos não-funcionais (RNF)
- RNF-01 (Portabilidade): o projeto tem de correr em Windows e macOS com um único comando (*single source of truth*).
- RNF-02 (Robustez de dados): tem de tolerar dados "sujos" (ex.: strings em campos numéricos do OSM).
- RNF-03 (Tempo de resposta): uma rota num raio de 1,5 km não pode exceder 2 segundos depois do mapa carregado.
- RNF-04 (Declive realista): quando as tags OSM `incline` são esparsas, o sistema tem de derivar um declive por aresta a partir de uma fonte externa de elevação.

4.2. Fluxo e persistência
- Ingestão: o OSMnx fala com a API Overpass sobre HTTP.
- Serialização: cada grafo de cidade fica em GraphML em `/data/osm_cache`.
- Enriquecimento de elevação: no arranque, o motor consulta o OpenTopoData (EU-DEM 25 m) para cada nó de cada cidade suportada e guarda o declive por aresta.
- Processamento: em runtime, cada grafo de cidade é carregado para RAM como NetworkX MultiDiGraph. A cidade ativa é selecionada por pedido através do campo `city` nos contratos da API.

5. MOTOR DE ROUTING (Lógica central)
O diferenciador do CityFlow é o algoritmo de pesos dinâmicos.

5.1. Função de penalização (heurística)
Para cada aresta (e), o custo (W) é:
    W(e) = Comprimento(e) × Penalização_total

Onde Penalização_total é o produto das restrições:
- Filtro binário (escadas): se avoid_stairs AND highway == steps → penalização = 10000
- Filtro de superfície: se surface NOT IN surface_preference → penalização × 3.5
- Filtro de declive: se ABS(grade) > max_incline → penalização × 15
- Filtro de declive suave: se ABS(grade) > max_incline × 0.75 → penalização × 3
- Filtro de largura: se width < min_width → penalização × 5

5.2. Limpeza de dados (parsing robusto)
O sistema aplica uma camada de parsing por regex para converter strings humanas do OSM ("1.5m", "narrow", "5%") em floats computáveis, evitando TypeErrors em runtime.

5.3. Enriquecimento real de elevação
No arranque, o motor consulta o OpenTopoData (gratuito, sem chave, conjunto EU-DEM 25 m) para cada nó, deriva `grade_abs` por aresta, limita a 25 % e suaviza arestas curtas, para que o ruído do DEM não produza declives falsos.

6. IMPLEMENTAÇÃO E DEPLOYMENT
6.1. Orquestração de ambiente (start.sh / start.ps1)
Para que um estagiário ou docente consiga correr o projeto sem configurar Python manualmente, o script de arranque:
- Deteta o SO e localiza os binários certos.
- Inicializa o venv e atualiza o pip.
- Instala os requirements.
- Arranca o uvicorn com `--reload` e o servidor de desenvolvimento Vite.

7. ESTRATÉGIA DE TESTES (Qualidade)
O backend tem de passar três níveis de validação no dashboard de developer (/docs):
- Teste de limite: passar coordenadas fora do raio. O sistema tem de devolver um 400 amigável em vez de crashar.
- Teste de perfil extremo: definir max_incline: 0.02. O motor tem de encontrar a rota mais plana, mesmo que seja 500 % mais longa.
- Teste de dados sujos: pedidos com strings inválidas em campos numéricos. O Pydantic bloqueia o pedido antes de chegar ao motor.

8. CONCLUSÃO
A arquitetura foi desenhada para ser extensível. Adicionar novos sensores (qualidade do ar, ruído, iluminação) no futuro requer apenas novas regras de penalização em router.py, mantendo o fluxo de navegação a montante intacto.
